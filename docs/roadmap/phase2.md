# Phase 2 — 실제 콘텐츠 로딩과 자원 수명

> **목표**: 디스크의 메시와 텍스처를 비동기로 읽어 화면에 표시하고,
> 로딩·실패·씬 전환 중에도 프레임 진행과 GPU 자원 수명이 안전함을 검증한다.
>
> 최종 산출물은 glTF 뷰어 기능 목록이 아니라 **CPU 로딩과 GPU 업로드의 경계,
> 명시적 애셋 소유권, 재현 가능한 로딩·전환 기준선**이다.

**상태**: 계획 초안. [phase1.md](phase1.md)의 구성에 맞춰 기존 [phase2.md](phase2.md)를 구체화한 별도 문서다.
아래 항목은 완료된 기능을 뜻하지 않는다. 기존 문서의 결정은 유지하되, 세부 지원 범위와 수치는 착수 게이트에서 확정한다.

## 1. 마일스톤과 게이트

| 마일스톤 | 답하려는 질문 | 산출물 |
|---|---|---|
| **2-A 메시 로딩** | 파일의 정점·인덱스를 프레임을 막지 않고 그릴 수 있나? | CPU 로더, staging 업로드, GPU Mesh, 비동기 완료 경로 |
| **2-B 텍스처** | 픽셀의 디코딩·업로드·샘플링 경계가 명확한가? | Texture, Sampler, descriptor, mipmap |
| **2-C 씬과 수명** | 실패·언로드·전환 중 GPU가 참조하는 자원이 안전한가? | SceneProxy, 씬 전환, 세대 핸들, 지연 파괴 |
| **2-D 벤치마크** | 로딩 비용과 프레임 영향이 재현되는가? | CLI, 고정 콘텐츠, 측정 표, Phase 3 인계 |

```text
Phase 1 인계 → 2-A → [게이트 A] → 2-B → [게이트 B] → 2-C → [게이트 C] → 2-D
             메시·비동기         텍스처·업로드         전환·수명         재현성
```

정확성·수명 게이트를 통과하지 못하면 다음 단계로 넘어가지 않는다.
성능 미달은 측정 구간과 원인을 기록하고, 해당 단계의 범위를 줄여 다시 검증한다.

### 착수 게이트 — Phase 1 인계

- Phase 1의 Job·Scheduler·Event 경로에 완료 대기, 종료, payload 소유권 계약이 있어야 한다.
- 잡 제출은 메인 스레드만 한다. worker는 중첩 잡을 제출하지 않는다.
- Phase 1의 기준선과 스트레스 결과, TSan 수행 여부 및 대체 검증을 인계한다.
- 기존 10만 삼각형 모드를 회귀 비교용으로 유지한다. 콘텐츠 모드의 성능과 직접 우열을 비교하지 않는다.
- 현재 Phase 1 문서는 1-A6까지 완료로 표시돼 있다. 1-B·1-C·1-D가 끝났다고 가정하고 착수하지 않는다.

## 2. 공통 원칙

| 원칙 | 계약 |
|---|---|
| **CPU와 GPU 분리** | `assets`는 파일 읽기·파싱·디코딩과 CPU 데이터 소유를 맡고 Vulkan/RHI 자원을 만들지 않는다 |
| **렌더링 소유권** | `renderer/world`는 GPU 자원을 소유하고 파일을 직접 읽지 않는다 |
| **핸들로 전달** | 이벤트에는 요청 ID·세대 핸들·상태를 넣고 가변 길이 데이터나 빌린 포인터를 넣지 않는다 |
| **프레임 경계 반영** | worker 결과의 게시, GPU 업로드 등록, World 갱신은 소유 스레드에서 처리한다 |
| **기존 씬 유지** | 새 씬이 CPU 로딩과 GPU 준비를 마치기 전까지 기존 씬을 계속 그린다 |
| **실패는 결과** | 잘못된 콘텐츠는 오류 상태로 끝낸다. 프로그래머 오류와 GPU 치명 오류 정책은 별개다 |
| **측정 후 최적화** | 전용 transfer queue·렌더 스레드·work stealing·lock-free 큐를 선행 구현하지 않는다 |

### 계층과 데이터 흐름

```text
content/                            런타임 콘텐츠
   ↓ platform 파일 읽기
assets                              CPU 파싱·디코딩 결과, AssetManager 소유
   ↓ 완료 이벤트에는 핸들만 전달
engine                              요청·실패·전환 정책과 논리 씬
   ↓ 물체별 SceneProxy로 단방향 복사
renderer/world                      GPU Mesh·Texture와 렌더링 상태
   ↓ RHI 업로드·그리기
graphics/backends/vulkan             메모리·명령·동기화
   ↓
화면
```

`engine/scene`은 graphics 타입을 모르고, renderer는 engine의 논리 씬 타입을 모른다.
SceneProxy는 renderer에 두며, 논리 씬의 메모리를 참조하지 않고 필요한 상태를 복사한다.
GPU 업로드에 필요한 CPU 데이터는 별도의 명시적 소유권 인계로 전달한다.

### 비동기 작업과 대기

- 메인 스레드가 요청을 등록하고 Scheduler에 작업을 제출한다.
- worker는 요청 전용 결과 저장소에 CPU 데이터를 완성한 뒤, 동기화된 경로로 완료 핸들을 게시한다.
- 완료 이벤트를 받기 전에는 소비자가 미완성 데이터를 읽지 않는다. 완료 결과는 소비 또는 폐기 확인 전까지 유지한다.
- 이벤트 push 실패 시 결과가 유실되지 않도록 재시도·거부·실패 중 정책을 정한다.
- **프레임마다 장시간 로딩 잡까지 포함한 전역 `wait_idle()`을 호출하지 않는다.**
  Phase 1의 짧은 프레임 작업 동기점과 로딩 완료 대기를 분리한다.
- 메인 스레드는 완료된 요청만 소비한다. worker 수가 1개인 경우에도 긴 로딩이 프레임 잡을 굶기지 않는지 검증하고,
  필요하면 로딩 전용 실행 자원을 최소한으로 분리한다.
- 종료 때는 새 요청을 막고 잡 완료를 기다린 뒤 결과 저장소·이벤트 큐·매니저를 해제한다.

## 3. 지표와 판정

| 지표 | 정의 |
|---|---|
| `request latency` | 로딩 요청 수락 → 최초로 표시 가능한 GPU 자원 준비 |
| `file read` | 파일 읽기 구간의 CPU 경과 시간 |
| `parse` / `decode` | 메시 파싱 / 텍스처 디코딩 구간의 CPU 경과 시간 |
| `upload CPU` | staging 복사·명령 기록·제출의 CPU 비용 |
| `upload GPU` | 업로드 명령 구간의 GPU timestamp 차이. 지원 여부를 표시 |
| `publish latency` | worker 완료 → 메인 스레드의 결과 반영 |
| `cpu frame` / `gpu frame` / `fence wait` | Phase 1과 같은 정의를 유지하는 프레임 지표 |
| `switch latency` | 씬 전환 요청 → 새 씬으로 교체된 첫 프레임 |
| `memory` | CPU 결과·staging·GPU 자원별 현재/최대 바이트와 생존 개수 |
| `failure` / `stale completion` | 오류로 끝난 요청 / 취소·언로드 이후 도착해 폐기한 완료 결과 수 |

- 프레임 지표는 워밍업 60프레임을 제외하고 중앙값·p95로 기록한다.
- 로딩 지표는 요청 자체를 표본으로 삼는다. 최초 로딩을 프레임 워밍업과 함께 버리지 않는다.
- 종료나 씬 전환 시 아직 집계되지 않은 GPU 표본의 처리 정책을 리포트에 명시한다.
- 프레임률은 실제 프레임 수/측정 경과 시간으로 계산한다. CPU 시간의 역수를 실제 fps로 표기하지 않는다.
- 성능 판정은 Release/RelWithDebInfo에서 한다. Debug+검증 레이어는 정확성 검증에 사용한다.
- 파일 캐시 상태, 콘텐츠 해시, 해상도, present 방식, CPU/GPU/드라이버/컴파일러를 함께 기록한다.
- 프레임 p95 목표, 업로드 바이트/프레임 상한, 완료 반영 개수/프레임 상한은 2-A1에서 정해 고정한다.

## 4. 2-A — 메시 파일과 비동기 로딩

**목표**: 파일에서 읽은 메시 하나를 그리면서 읽기·파싱·업로드·표시의 경계를 검증한다.

**제약**

- 기존 문서의 cgltf 채택을 유지한다. 의존성 버전 또는 커밋과 라이선스를 고정한다.
- 초기 범위는 정적 삼각형 메시, 위치, 인덱스, 노드 변환, 단색이다. UV는 2-B 입력을 위해 보존한다.
- `.gltf`/`.glb`, 외부 버퍼·내장 버퍼의 지원 조합은 2-A1에서 고정하고 fixture로 남긴다.
- 지원하지 않는 primitive·확장·속성 조합은 식별 가능한 오류로 거부한다. 조용히 일부를 생략하지 않는다.
- 인덱스가 없는 메시도 명시적으로 처리하고, 인덱스가 있으면 버퍼와 indexed draw 경로를 쓴다.
- CPU 파싱 중에는 GPU API를 호출하지 않는다. 업로드는 우선 기존 graphics queue를 사용한다.
- 기존 깊이 이미지·깊이 테스트는 재사용한다. 카메라는 고정하고 최소 view/projection만 추가한다.

**순서**: 2-A1 → 2-A2 → 2-A3 → 2-A4 → 2-A5 → 2-A6 → 2-A7

### 2-A1 — 입력 계약과 비교 조건

- **목표:** 무엇을 읽고 어떤 상태를 성공으로 판단할지 먼저 고정한다.
- **작업 내용:** 지원 파일·속성·인덱스·변환 범위, 전체 실패 정책, 경로 기준을 정한다.
  작고 정상인 파일, 손상 파일, 지원 밖 파일, 경로 누락 파일을 준비하고 예산·측정 환경을 기록한다.
- **완료 조건:** 지원 표, fixture 목록·해시·이용 조건, 오류 분류, 프레임·업로드 예산이 문서에 있다.

### 2-A2 — CPU 애셋과 요청 소유권

- **목표:** 요청·결과·언로드를 세대 핸들로 추적한다.
- **작업 내용:** `assets`에 CPU 메시 데이터와 요청 레지스트리를 둔다.
  `Queued → Loading → CpuReady` 및 `Failed` 상태를 정의하고 GPU 준비 상태와 구분한다.
  AssetManager가 소유하며 명시적 `unload()`를 제공한다.
- **완료 조건:** 해제된 핸들을 resolve할 수 없고, 슬롯 재사용 후 이전 완료 결과가 새 요청을 덮어쓰지 않는다.

### 2-A3 — glTF CPU 파싱

- **목표:** 파일에서 GPU와 무관한 메시 데이터를 만든다.
- **작업 내용:** platform 파일 I/O를 통해 읽고 cgltf를 감싼 로더로 정점·인덱스·노드 변환·경계를 추출한다.
  accessor 범위, stride, 인덱스 범위, 크기 산술과 파일 참조 경로를 검증한다.
- **완료 조건:** fixture의 정점·인덱스·변환·AABB가 기대값과 같고, 손상·미지원 입력이 오류 결과로 끝난다.

### 2-A4 — Staging과 GPU Mesh 업로드

- **목표:** CPU 배열을 device-local 정점·인덱스 버퍼로 옮긴다.
- **작업 내용:** RHI에 필요한 buffer copy, index binding, indexed draw를 추가한다.
  host-visible staging에 복사하고 GPU 복사와 이후 정점·인덱스 읽기 사이의 동기화를 정의한다.
  제출 fence 완료 전에는 staging을 재사용하거나 해제하지 않는다.
- **완료 조건:** 업로드한 메시가 기존 graphics queue에서 그려지고, staging 조기 해제와 검증 레이어 오류가 없다.

### 2-A5 — GPU Mesh와 고정 카메라

- **목표:** 공유 단위 삼각형 대신 파일별 GPU Mesh를 선택해 그린다.
- **작업 내용:** renderer가 GPU Mesh 핸들과 draw 범위를 소유한다.
  노드 변환과 고정 카메라의 view/projection을 적용하고, 월드 AABB와 컬링을 같은 좌표계로 맞춘다.
  카메라 프러스텀도 실제 변환에 맞춰 갱신하며 기존 clip-space 고정 프러스텀을 그대로 쓰지 않는다.
- **완료 조건:** 서로 다른 두 메시가 올바른 위치·깊이로 표시되고 컬링 off/on의 보이는 결과가 일치한다.

### 2-A6 — Scheduler와 완료 이벤트 연결

- **목표:** 로딩 요청 후에도 기존 화면을 계속 그린다.
- **작업 내용:** 메인 스레드가 파싱 잡을 제출하고 worker는 완료 핸들을 MPSC 이벤트 경로로 게시한다.
  프레임 경계에서 결과를 받아 예산 안에서 업로드를 진행하고, GPU 완료 후에만 draw 가능 상태로 게시한다.
  단일 대형 자원은 업로드 분할 또는 명시적 크기 제한으로 처리한다.
- **완료 조건:** 느린 I/O·파싱을 주입해도 프레임이 계속 진행되고, 긴 로딩에 대한 전역 잡 대기가 없다.
  worker 수 1/N, 이벤트 혼잡에서도 완료가 유실되지 않고 예산 초과가 보고된다.

### 2-A7 — 오류와 종료 검증

- **목표:** 실패한 로딩이 기존 씬과 프로세스 수명을 깨지 않는다.
- **작업 내용:** 파일 없음·손상·지원 밖 데이터·로딩 중 종료를 검증한다.
  읽기·파싱·업로드·전체 지연과 정적 씬 대비 프레임 영향을 기록한다.
- **완료 조건:** 실패 시 기존 씬이 유지되고 원인이 보고된다. 종료 시 잡·결과·staging·GPU 자원의 소유자가 남지 않는다.

**게이트 A — 텍스처를 얹을 것인가**

- 메시·컬링·동기화 검증 통과, 프레임 진행과 예산 충족 → 2-B로 진행한다.
- 업로드가 프레임을 막음 → 분할·상한·완료 반영 정책을 먼저 수정한다. 전용 큐를 즉시 추가하지 않는다.
- 로더 실패가 프로세스를 종료하거나 완료 결과가 유실됨 → 2-A를 먼저 고친다.
- 성능 편차가 크면 파일 캐시·GPU 업로드·worker 경쟁을 분리 측정하고 기준선을 다시 잡는다.

## 5. 2-B — 텍스처

**목표**: 파일 픽셀을 GPU 이미지로 옮겨 UV로 샘플링하고 비용과 수명을 측정한다.

**제약**

- 조명 없는 단색·base color 텍스처만 지원한다. PBR·normal map·투명도 정렬은 제외한다.
- CPU 이미지 디코더는 2-B1에서 버전·라이선스·오류 정책을 정한다.
- assets는 CPU 픽셀을 만들고, renderer가 Image·ImageView·Sampler·descriptor를 소유한다.
- 색 데이터와 일반 수치 데이터의 색 공간 정책을 구분한다.
- mipmap 생성은 필수다. GPU 생성 기능이 없는 형식·장치의 대체 경로 또는 지원 제한을 명시한다.

**순서**: 2-B1 → 2-B2 → 2-B3 → 2-B4

### 2-B1 — 디코딩과 텍스처 계약

- **목표:** CPU 픽셀 형식과 파일 참조 범위를 고정한다.
- **작업 내용:** glTF 이미지 참조 방식, 지원 파일 형식, 채널 변환, 최대 크기, UV·색 공간 정책을 정한다.
  이미지 없음·손상·과대 크기의 오류 또는 대체 텍스처 정책을 정한다.
- **완료 조건:** fixture의 크기·픽셀·UV 방향을 확인하고, 실패가 원래 요청과 연결돼 보고된다.

### 2-B2 — 이미지 업로드와 mipmap

- **목표:** staging의 픽셀을 샘플링 가능한 이미지로 만든다.
- **작업 내용:** 기존 `rhi/resource/image.hpp`를 확장해 필요한 밉·복사 범위를 표현한다.
  buffer-to-image copy, layout 전환, mipmap 생성, shader 읽기까지의 동기화를 구현한다.
- **완료 조건:** 각 밉의 크기·전환이 검증되고 업로드 완료 전 샘플링과 staging 조기 해제가 없다.

### 2-B3 — Sampler와 descriptor 연결

- **목표:** 셰이더가 올바른 텍스처를 UV로 읽는다.
- **작업 내용:** RHI와 renderer에 필요한 sampler·descriptor·pipeline layout 경로를 추가한다.
  정점 입력에 UV를 연결하고 base color 텍스처를 샘플링한다.
  프레임에서 사용 중인 descriptor를 덮어쓰지 않도록 갱신·해제 시점을 정한다.
- **완료 조건:** 두 물체에 서로 다른 텍스처가 표시되고 fallback·밉 선택·UV 방향이 fixture와 일치한다.

### 2-B4 — 메모리와 업로드 측정

- **목표:** 해상도와 밉 수에 따른 비용을 설명한다.
- **작업 내용:** decode 시간, upload CPU/GPU, staging·GPU 바이트, 요청 지연과 프레임 p95를 기록한다.
- **완료 조건:** 작은 텍스처와 큰 텍스처의 비교 표가 있고, 업로드량을 제한했을 때 메모리 상한과 프레임 예산이 지켜진다.

**게이트 B — 여러 씬을 전환할 것인가**

- 텍스처와 descriptor의 수명·동기화 검증 통과 → 2-C로 진행한다.
- 과다 메모리·긴 프레임 → in-flight 업로드 수·바이트 예산부터 조정한다.
- 디코딩이 병목 → 비용과 지원 범위를 기록한다. 스트리밍·압축 텍스처는 후속 Phase로 남긴다.

## 6. 2-C — 여러 메시와 씬 전환

**목표**: 새 씬 로딩, 기존 씬 표시, 전환과 언로드를 명시적 수명 계약으로 닫는다.

**제약**

- 논리 씬의 최소 물체 목록과 변환만 도입한다. 범용 component/ECS 체계는 만들지 않는다.
- SceneProxy는 물체별 초기 상태 복사다. 이 단계에서는 정적 씬만 다루고 변경 전파 체계는 별도 요구가 생길 때 설계한다.
- SharedAssetManager는 앱 수명, LocalAssetManager는 씬 수명이다. 처음부터 범용 공유·참조 카운팅을 넣지 않는다.
- 새 씬은 전체 준비 후 한 프레임 경계에서 교체한다. 실패하면 기존 씬을 유지한다.
- 언로드는 신규 사용 차단과 실제 GPU 메모리 회수를 구분한다.

**순서**: 2-C1 → 2-C2 → 2-C3 → 2-C4 → 2-C5

### 2-C1 — SceneProxy 경계

- **목표:** 논리 씬과 렌더링 World가 서로의 내부 데이터를 참조하지 않는다.
- **작업 내용:** 엔진의 씬 물체에서 renderer 소유 프록시로 변환·메시·머티리얼 식별 정보를 복사한다.
  assets CPU 핸들과 renderer GPU 핸들의 구분과 변환 지점을 정한다.
- **완료 조건:** renderer에서 engine 헤더를 포함하지 않고, 논리 씬은 graphics 핸들을 보관하지 않는다.

### 2-C2 — 씬별 애셋 소유권

- **목표:** 공용 자원과 씬 전용 자원의 해제 범위를 구분한다.
- **작업 내용:** manager별 소유 핸들 목록, 명시적 unload 순서, CPU 데이터 보존·폐기 정책을 둔다.
  씬이 GPU 준비 완료 후 CPU 파싱 데이터를 버릴 수 있는지 실제 참조를 기준으로 결정한다.
- **완료 조건:** 씬 언로드가 공용 자원을 해제하지 않고, 무효 핸들 resolve와 중복 해제를 거부한다.

### 2-C3 — 씬 전환과 늦은 완료 결과

- **목표:** 로딩 중 재요청·실패에도 현재 씬이 유지된다.
- **작업 내용:** 요청 세대와 씬 세대를 함께 검사한다. A 표시 중 B 로딩, B 로딩 중 C 요청,
  B 실패·언로드 후 도착한 완료 이벤트를 처리한다. worker 강제 중단 대신 늦은 결과를 안전하게 폐기한다.
- **완료 조건:** 최신 유효 요청만 게시되고, 미완성 B가 보이거나 C를 덮어쓰지 않는다.

### 2-C4 — GPU 자원 지연 파괴

- **목표:** 마지막 GPU 사용이 끝나기 전에는 자원을 파괴하지 않는다.
- **작업 내용:** World에서 신규 draw 참조를 제거한 뒤 해당 자원을 참조한 모든 in-flight 제출 완료를 확인한다.
  staging·descriptor·ImageView·Image·Buffer·메모리를 의존 관계에 맞춰 해제한다.
  기존 ResourceDeletion을 사용할 때 선택한 frameIndex가 마지막 사용을 대표한다는 근거를 둔다.
- **완료 조건:** 다중 프레임 in-flight, 반복 전환, 업로드 중 언로드에서 use-after-free·이중 해제·VUID가 0이다.

### 2-C5 — 전환·종료 스트레스

- **목표:** 정상 경로뿐 아니라 수명 경계의 실패를 반복 검증한다.
- **작업 내용:** 정상·손상 씬을 섞어 100회 전환하고 로딩·업로드·전환 각 시점에 종료를 주입한다.
  CPU/GPU 생존 자원 수와 바이트가 정리 완료 후 기준 상태로 돌아오는지 확인한다.
- **완료 조건:** 완료 유실·stale 결과 게시·검증 레이어 오류가 0이고 지속적인 메모리 증가가 없다.

**게이트 C — 기준선으로 고정할 것인가**

- 100회 전환·종료 스트레스, 자원 수명, 오류 정책 통과 → 2-D로 진행한다.
- 파괴 시점이 불명확하거나 메모리 증가 → 2-C로 돌아간다. 캐시로 증상을 숨기지 않는다.
- 정적 씬 성능만 느림 → 회귀 원인을 기록한다. 배칭·인스턴싱은 Phase 3 후보로 넘긴다.

## 7. 2-D — 로딩과 전환 벤치마크

**목표**: 같은 콘텐츠와 조건으로 로딩 지연·프레임 영향·메모리 비용을 재현한다.

**제약**

- Phase 1 CLI와 보고 형식을 확장한다. 아래 옵션은 구현 예정 계약이며 현재 지원을 뜻하지 않는다.
- 작은 단색 메시, UV·텍스처 메시, 여러 메시 씬, 실패 fixture를 고정한다.
- 같은 조건을 3회 이상 반복한다. cold/warm 캐시를 섞지 않고, cold 조건을 통제하지 못하면 명시한다.
- GPU validation ON 정확성 실행과 OFF 성능 실행을 분리한다.

**순서**: 2-D1 → 2-D2 → 2-D3 → 2-D4

### 2-D1 — 재현 CLI

- **목표:** 씬과 로딩·전환 설정을 명령행으로 재현한다.
- **작업 내용:** `--scene`, `--next-scene`, 전환 시점, warmup·측정 프레임 수,
  업로드 예산·in-flight 요청 수·worker 수를 표현하고 적용 설정을 출력한다.
- **완료 조건:** 잘못된 입력을 거부하고 설정·fixture 해시가 리포트에 그대로 남는다.

### 2-D2 — 자동 종료와 표본 확정

- **목표:** 로딩·표시·전환의 종료 조건을 구분하고 한 번의 리포트를 남긴다.
- **작업 내용:** 성공·실패 요청 수, 실제 경과 시간, 완료 프레임 수, CPU/GPU 표본 수를 집계한다.
  GPU 완료를 기다려 남은 표본을 수집하되 종료 정리 시간은 정상 프레임 시간에 섞지 않는다.
- **완료 조건:** 실행이 스스로 끝나고 요청 총계와 종료 상태가 일치한다.

### 2-D3 — 비용과 회귀 비교

- **목표:** 로딩 없는 상태와 로딩·전환 중 상태의 차이를 숫자로 설명한다.
- **작업 내용:** 같은 콘텐츠의 정적 표시, 추가 로딩, 전환을 비교한다.
  worker 1/N, 업로드 예산, 콘텐츠 크기를 바꾸고 3회 이상의 p50·p95·편차·최대 메모리를 기록한다.
  별도로 기존 삼각형 모드를 같은 빌드·환경에서 재측정한다.
- **완료 조건:** 지표 정의와 캐시 조건이 같은 비교 표 및 예산 초과 원인이 남는다.

### 2-D4 — 기준선과 Phase 3 인계

- **목표:** 다음 최적화의 근거와 남은 제한을 고정한다.
- **작업 내용:** `docs/benchmarks/phase2-baseline.md`를 후속 구현 시 신규 작성한다.
  지원 범위, fixture, 게이트 A·B·C 판정, 성능·메모리 표와 미해결을 기록한다.
- **완료 조건:** 콘텐츠별 병목이 파일 읽기·파싱·디코딩·업로드·그리기 중 어디인지 근거로 설명된다.

**Phase 2 완료 정의**

- [ ] 지원 범위 안의 파일에서 읽은 메시·텍스처가 올바르게 표시된다.
- [ ] 잘못된 파일과 미지원 데이터는 식별 가능한 오류로 끝나며 기존 씬이 유지된다.
- [ ] CPU 로딩·GPU 업로드·렌더링의 소유권과 상태 전이가 구분된다.
- [ ] 느린 로딩 중에도 프레임이 진행되고 정한 업로드·프레임 예산이 검증된다.
- [ ] 논리 씬과 World가 SceneProxy를 통해 연결되고 CPU/GPU 핸들이 구분된다.
- [ ] 반복 전환·언로드·종료에서 stale 결과 게시와 자원 누수가 없다.
- [ ] Debug 검증 레이어 VUID/ERROR가 0건이다.
- [ ] 동시성 스트레스와 가능한 환경의 TSan 또는 대체 검증 결과가 기록된다.
- [ ] Release/RelWithDebInfo 기준선과 기존 삼각형 모드 회귀 결과가 있다.
- [ ] Phase 3가 쓸 병목 판정과 지원 제한이 문서에 있다.

## 9. 미해결 — 결정 시점

| 질문 | 결정 시점 | 초안의 가정 |
|---|---|---|
| glTF와 외부·내장 데이터의 최소 지원 조합은? | 2-A1 | 지원 표와 fixture로 고정, 미지원은 오류 |
| 좌표계·노드 계층·카메라를 어떻게 맞추나? | 2-A1·2-A5 | 정적 노드 변환 누적, 고정 카메라, 컬링과 같은 좌표계 |
| 긴 로딩과 프레임 잡이 같은 worker를 써도 되나? | 2-A6 | 전역 대기를 피하고 starvation 측정 후 최소 분리 |
| 요청 수·staging 바이트·GPU 업로드 예산은? | 2-A1·2-A6 | 대상 환경과 fixture에 맞춰 수치 확정 |
| 매우 큰 단일 자원은? | 2-A4·2-A6 | 분할 또는 명시적 제한, 무제한 단일 프레임 업로드 금지 |
| CPU 결과는 업로드 후 언제 버리나? | 2-C2 | 재로딩 정책과 마지막 참조를 확인해 폐기 |
| 디코더와 이미지 포맷은? | 2-B1 | 버전·라이선스·실패 정책을 함께 확정 |
| GPU mipmap 생성 미지원 장치는? | 2-B2 | CPU 대체 또는 지원 제한을 명시 |

| 씬 전환 중 같은 자원을 공유하나? | 2-C2 | 씬 전용·앱 공용 수명부터 구현, 자동 refcounting 없음 |
| 어떤 fence가 마지막 사용을 대표하나? | 2-C4 | 모든 관련 제출 완료 근거를 기록 |
