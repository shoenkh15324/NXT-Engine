# Phase 1 1-A 기준선

> 측정일: 2026-11-23
>
> 이 문서는 [phase1.md](../roadmap/phase1.md) 1-A6의 산출물이다. 게이트 A 판정의 근거이며
> 1-B와 1-D가 비교할 첫 기준선이다.
>
> **판정에 쓰는 세션은 §3의 immediate(주사율 고정 없음)이다.** §6의 FIFO 세션은 고정
> 주사율에서의 참고값이고, 병목 판정과 GPU 비교에 쓰지 않는다.

## 2. 측정 방법

1. `cmake --preset msvc-bench`
2. `cmake --build --preset msvc-bench --target sandbox`
3. `sandbox --objects 100000 --culling {off|on} --present immediate --log-level info`
4. 컬링 off/on 각 7회, 회차마다 40초 실행 후 창을 닫아(WM_CLOSE) 정상 종료한다.
5. 각 회차 로그의 `frame:` 줄(1초 창)에서 첫 창(워밍업 직후 partial)과 마지막 창(종료
   partial)을 버린다.
6. 회차 대표값
   - `cpu/gpu/fence p50` = 창별 p50의 **중앙값**
   - `cpu/gpu/fence p95` = 창별 p95의 **중앙값**(표의 p95)과 **최댓값**(요약의 p95 최댓값)
   - `fps` = `1000 / cpu p50`으로 계산한 **상한**
   - `throughput` = fps × 100,000 objects/s
7. 같은 설정 7회의 p50 편차 = (최댓값 − 최솟값) / 7회 중앙값 × 100%.

> **fps가 상한인 이유.** 이 세션의 `FrameStats`는 표본 버퍼가 240개에서 포화돼 `n=240`을
> 기록했다. 실제 프레임은 그보다 많았고, 로그만으로 정확한 프레임 수를 복원할 수 없다.
> 프레임 주기는 cpu frame보다 짧을 수 없으므로 `1000 / cpu p50`은 fps의 상한이다.
> 같은 날 `FrameStats`에 창 프레임 카운터를 추가했으므로, 이후 측정은 `n`이 실제
> 프레임 수가 된다. 정확한 fps는 1-D1 · 1-D2의 벤치마크 모드에서 확정한다.

## 4. 설정별 요약 (immediate)

`fps*` · `throughput*`은 §2의 상한 계산이다.

| 설정 | draws | cpu p50 | cpu p95(중앙값) | cpu p95(최댓값) | gpu p50 | gpu p95(중앙값) | fence p50 | fps* | throughput* | p50 편차 |
|---|---|---|---|---|---|---|---|---|---|---|
| culling off | 100000 | 3.845 | 4.09 | 9.38 | 1.040 | 1.27 | 0 | ≤ 260 | ≤ 26.0M | 1.3% |
| culling on | 65025 | 2.890 | 3.06 | 5.39 | 0.680 | 0.68 | 0 | ≤ 346 | ≤ 34.6M | 2.1% |

- `fence p50`이 0이므로 `cpu frame`은 fence 대기를 포함하지 않는다. 즉 cpu p50은 실제
  CPU 작업 시간이다.
- 컬링 효과: draws −35.0%, cpu p50 −24.8%, gpu p50 −34.6%. 회차 편차(1.3%, 2.1%)보다
  훨씬 큰 차이라 설정 효과로 볼 수 있다.
- 컬링 on의 처리량은 총 오브젝트 기준이다. visible 기준으로는 약 22.5M visible/s이다.

## 5. 게이트 A 판정

| 조건 | 판정 |
|---|---|
| `cpu frame`이 `gpu frame`보다 크고 fps를 제한한다 | CPU-bound → 1-B 전체 진행 |
| `gpu frame`이 `cpu frame` 이상이거나 `fence wait`가 크다 | GPU-bound → 1-B는 인프라(1-B1~1-B7, 1-B9)만, 1-B8 생략 |
| 둘 다 16.67ms 미만이고 fps도 충분하다 | 병목 없음. 오브젝트 수 스윕으로 포화 지점을 확인한 뒤 판정 |
| 같은 설정 3회 이상 p50 편차 > 10% | 1-A5로 회귀. 이 숫자는 기준선이 아니다 |

16.67ms(60Hz)는 병목 판정식이 아니라 목표 예산 플래그다.

**판정**: **CPU-bound.** 1-B 전체를 진행한다.

**근거**:

- immediate에서 `fence p50 = 0`이므로 cpu frame은 순수 CPU 작업이다(3.845ms / 2.890ms).
- 같은 조건의 gpu frame은 1.040ms / 0.680ms다. CPU가 GPU보다 **3.7배 / 4.3배** 무겁고,
  프레임 처리량의 상한을 CPU가 결정한다(≤260fps / ≤346fps).
- 60fps 예산 대비로는 4배 이상 여유가 있다. 즉 "지금 60fps를 못 내는 병목"은 없고,
  **엔진의 최대 처리량을 정하는 쪽이 CPU**라는 뜻이다. 1-B의 목표(CPU 경로 병렬화)와
  일치한다.
- 컬링 on에서 cpu p50이 2.890ms로 줄어 CPU 경로에 컬링이 실제로 작용한다. 다만
  `record` 구간이 컬링과 명령 기록을 함께 재고 있어, 컬링 자체의 비용은 분리되지 않았다.
  draw 기록이 선형이라고 가정하면 컬링은 약 0.39ms(on cpu의 13%)로 추정된다. 이번에
  `cull` 구간을 Profiler에 추가했으므로 1-B8은 이 구간을 기준선으로 쓴다.
- 회차 편차 1.3% / 2.1%로 10% 이내다. 기준선으로 쓸 수 있다.

**다음 단계**: 1-B1부터 진행한다. 1-B8(병렬 컬링)을 포함한다. 1-B8의 1차 목표는
100k에서 약 0.39ms(CPU의 13%)인 `cull` 구간을 줄이는 것이다.

## 6. 참고: 고정 주사율(FIFO) 세션

같은 날 `--present fifo`로 먼저 측정한 값이다. 기본 창 설정(60Hz)에서의 참고값이며,
**병목 판정과 GPU 비교에는 쓰지 않는다.**

| 설정 | draws | cpu p50 | cpu p95(최댓값) | gpu p50 | fence p50 | fps | p50 편차 |
|---|---|---|---|---|---|---|---|
| culling off | 100000 | 16.615 | 23.51 | 4.665 | 12.820 | 61 | 0.06% |
| culling on | 65025 | 16.610 | 35.13 | 3.515 | 13.730 | 61 | 0.54% |

- `cpu p50 ≈ 16.62ms`는 1/60초와 같다. `fence p50 = 12.8ms`가 프레임의 77%이고,
  `16.62 − 3.85 = 12.78ms`가 immediate의 cpu p50과 일치한다. FIFO에서 cpu frame은
  CPU 작업이 아니라 vsync 대기를 잰 값이다.
- 같은 씬·같은 명령인데 gpu p50이 immediate(1.04ms)보다 4.5배 크다. vsync로 GPU가 대부분
  쉬면 클럭이 낮아져 timestamp 구간이 늘어난다. 두 세션의 GPU 수치를 직접 비교하지 않는다.
- 컬링 on에서 cpu p50이 동일한 것은 fence가 차이를 흡수했기 때문이다. 실제 CPU 작업은
  이 세션에서도 줄었다(record 3.76ms → 2.87ms).

## 7. 한계

- `fps*`는 상한이다. §2의 포화 문제 때문에 실제 fps는 240 이상임만 확인됐다. 정확한 값은
  1-D2에서 확정한다.
- 1초 창의 p95는 최근 240표본 기준이다. 260~346fps에서는 약 0.7~0.9초에 해당한다.
- 창별 p95의 최댓값(9.38ms 등)은 1초에 한 번 있는 로그 I/O 같은 단발 지연에 민감하다.
  그래서 §4는 중앙값과 최댓값을 함께 적는다.
- immediate는 tearing이 생길 수 있다. 측정값에는 영향이 없다.
- Debug 수치는 성능이 아니므로 이 문서에 쓰지 않는다.
- 워밍업은 60프레임 고정이다. 셰이더 캐시·클럭 부스트가 더 오래 걸리면 p50 편차가 커질 수 있다.
